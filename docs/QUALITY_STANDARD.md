# Mova 产品目标与上架质量标准

本文件是长期质量约定，适用于每次功能、性能、视觉、依赖和平台更新。描述的是目标与验收要求，不代表当前版本已经达到。当前单项整改进度见 `docs/specs/`，不得把历史通过记录当作当前构建的验证结果。

## 1. 产品目标与优先级

Mova 面向公开上架、软件售卖和长期维护，是连接用户授权私人媒体来源的跨平台影视客户端，不托管或出售影视内容。当前验收平台为 Windows 与 Android；未来平台须完成独立验证后才能宣传支持。

优先级：用户数据与安全 > 可播放及故障恢复 > 流畅稳定 > 功能一致与易用 > 视觉效果 > 新增功能。收费、商店上架和宣传不降低此标准。软件质量不能以功能数量、测试数量或峰值网速代替。

## 2. 架构方向（目标，不是现状声明）

- 双端统一控件语义、观看状态、服务器代理规则、缓存策略与统计口径；允许按平台适配交互和底层实现，不强求全部经过同一个中转。
- Android 默认 Exo，优先原生取流与 Media3 原生缓存；mpv 作为明确的兼容选择。Windows 使用既有原生 libmpv 播放器，优先成熟取流能力。
- 本机 HTTP 中转只在必要的协议处理、路由或共享缓存场景保留。迁移 Windows 现有路径前必须验证鉴权、切服务器、缓存、统计和播放稳定性，不以“原生一定更快”为依据。
- 优先现有组件、平台能力和成熟依赖；不为规模预建复杂架构。底层变更必须有可复现问题及对照证据。
- 网络实际下载、播放器缓冲交付、本地缓存命中是不同指标，必须分开记录。缓冲满停止取流显示零速是正常状态，不得用码率估算伪装实时网速。

## 3. 每次更新必须执行

1. 阅读本标准与相关规范，明确受影响平台、路径、用户行为和数据兼容范围。
2. 功能修复记录复现条件；性能优化先记录基线及假设。复杂改动使用 `docs/CHANGE_SPEC_TEMPLATE.md`，小改动可在交付记录中填写同样的相关项。
3. 分开修改与验证稳定性、功能和视觉；不要同时改变多个变量后将改善归因于其中一个。
4. 运行匹配风险的测试、静态检查和平台构建。共享业务变更核对双端；源码接线检查不能代替行为测试或原生真机测试。
5. 代码变更按用户要求在目标端本地部署并复测；用户限定单端时不部署另一端。程序占用、缺设备或权限未确认时说明未部署，不强制结束用户进程或绕过安全审核。纯文档变更无需构建安装包。
6. 把结果写入规格/交付记录，区分“已修改、已测试、已构建、已部署、已实测”。缺失验证不得算通过。
7. 有退步、数据损失或安全风险时先修复/回退本次改动，保留用户其他工作。提交、推送和发布仍需明确授权。

## 4. 性能验收

固定路径：启动与后台恢复；首页大海报连续滑到发现页底部再返回；发现/继续播放的全部列表进出；详情页进出与剧集切换；搜索结果滚动；设置右栏和二级菜单滚动；播放器进出。

- 使用真实设备 profile/release，记录设备、系统、分辨率、刷新率、构建标识、缓存冷热、数据规模和采样方式；每条受影响路径至少重复三次，使用相同条件比较。
- 按刷新率计算帧预算（60 Hz 约 16.7 ms，120 Hz 约 8.3 ms），分别记录 Flutter UI/raster 耗时、p95/p99、超预算比例、长帧及内存；原生呈现/解码另采样，不能只看平均 FPS。
- 上架目标：常规浏览接近设备刷新率，无可重复的应用引起的明显停顿；后台恢复不无故重新加载所有海报，内存不随重复进出持续增长。
- 同条件 p95 帧耗时退步超过 5%、慢帧比例增加超过 1 个百分点，或出现新的可重复卡顿，必须复测定位。重复确认是本次改动导致的退步时阻止正式发布；这些数值是调查门槛，不是已达成的实测结果。
- 首次建立基线时必须同时审查绝对体验，不能把已经卡顿的基线当作合格标准。外部设备/系统干扰需记录并控制后重测。
- 延续固定玻璃材质约定；恢复实时背景采样或高成本效果须获得需求授权并有双端性能证据，不能为视觉牺牲已验证的流畅度。

## 5. 播放与网络验收

受控测试覆盖 HTTP/HTTPS、重定向、鉴权失效、Range 支持/不支持、超时、断连、直连/服务器代理、本地完整/部分缓存和无缓存。真机覆盖常用格式、音轨、字幕及产品声称支持的高规格资源。

- 验证开播、暂停恢复、拖动、切集、切服务器、后台恢复、退出与自然播完；不能把缓冲显示为用户暂停，不能无限重试或静默切引擎。
- 记录首帧时间、缓冲次数与总时长、掉帧、实际网络读取、缓存命中及恢复结果。双端速度对照须同资源、同路由、同缓存条件，不能比较本地读取与源站下载。
- 不并行重复拉取同一播放区间；预加载有界且不能抢占当前播放。缓存必须遵守容量、计量网络、清理、资源/鉴权隔离与旧格式兼容要求。
- 播放/缓存/探测遵守同一服务器代理选择；不得为了兼容关闭 TLS 校验。新增明文 HTTP 范围、权限或信任范围必须单独说明并取得必要授权，不能从一般优化请求推定同意。
- 正式候选版本每端至少完成一段 30 分钟连续播放及操作复测；播放管线变更另做至少 60 分钟长测，检查资源泄漏、后台恢复与记录同步。
- 在源站吞吐足够、网络稳定的受控条件下，不允许可重复的应用引起的卡死、错误停止或反复缓冲。源站不足、网络波动和设备解码限制需有证据、可理解的提示及恢复入口，不承诺所有外部资源均流畅。
- HDR/Dolby Vision 宣传必须有实际设备输出证据，不能仅根据资源标签或解码成功宣称激活。

## 6. 状态、隐私与发行

- 观看进度先可靠保存本地、立即通知继续播放/详情/全部剧集/播放器，再异步同步服务器；失败可重试，不撤销本地已保存进度。集号选择、日历、待看和弃剧规则不能各页面各自判断。
- 数据迁移与回退需测试；不能假定换回旧安装包就能安全读新格式。诊断不泄露 URL 中的凭据、鉴权头、Token 或私人媒体信息，不新增未获同意的遥测上传。
- 公开售卖前核对实际支持平台、第三方依赖/字体/Logo 许可、隐私说明、内容来源、签名与升级、渠道政策及用户支持/故障反馈流程。涉及法律和商店政策按当次最新规则另行核查，不把本标准当合规结论。

## 7. 正式发布阻断项

以下任一项未关闭，不得将版本标记为正式上架就绪：可复现崩溃/卡死、关键资源播放失败、观看记录丢失、代理/鉴权错误、隐私安全问题、已确认性能退步、迁移/签名升级失败、关键平台未构建或未实测、声称支持的能力无证据。

非关键限制可明确标为已知限制，写清影响、恢复方式和后续事项；不能用“后续优化”隐藏阻断项。内部测试构建可以保留未完成项，但必须明确不是正式合格版本。

## 8. 每次交付记录

| 项目 | 必填内容 |
|---|---|
| 改动 | 原因、范围、影响平台、构建/提交标识 |
| 验证 | 命令结果、设备、路径、行为测试及对照数据 |
| 部署 | 哪端实际安装、数据是否保留、未部署原因 |
| 风险 | 已知限制、安全授权、兼容与回退措施 |
| 结论 | 当前阶段完成程度、阻断项、未执行检查及下一步 |

文档规则由开发流程执行，目前不等于自动 CI 发布门禁；未来自动化时需单独实现并验证，不得宣称现已自动阻止发布。

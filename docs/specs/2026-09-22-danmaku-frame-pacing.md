# Windows 原生播放器：弹幕滚动平滑度（帧节拍与刷新率不匹配）

## 基本信息

- 标题：弹幕滚动「还是不够平滑」——帧节拍与显示器刷新率不同源导致的 2:3 拍频抖动
- 日期：2026-09-22
- 状态：**已实现（85Hz 固定周期节拍时钟），已部署待实机确认观感**
- 影响平台：Windows 原生播放器（`MovaNativePlayer.exe`）；Android / Flutter 侧不受影响
- 关联：接续 `docs/specs/2026-09-19-danmaku-layout-and-smoothness.md`（那一轮修的是
  「看不清」+「时间源粒度」，本轮是它之后仍然存在的残量）

## 背景与问题

用户反馈（原话）：「目前弹幕的滚动平滑度还是不够，检查一下，现在的弹幕滚动平滑度情况」。

### 现状：所有既有指标都是「合格」

`tool/probe_danmaku_layout.py --label current`（合成 1080p 场景，16 个采样窗口）：

| 指标 | 实测 | 既有判据 | 结论 |
|---|---|---|---|
| `avg` 帧间隔 | **16.23–16.35 ms**（≈61.3 fps） | ≤ 18ms | OK |
| `draw` 峰值 | 2.61 ms | ≤ 12ms | OK |
| `post` 峰值 | 0.71 ms | — | OK |
| `gap` 峰值 | 24.0 ms（60 帧里 4 帧 >20ms） | 只看均值 | OK |
| `late33` | **0** | < 3 | OK |
| `drop`（mpv 丢帧） | **0** | 0 | OK |
| `overlap` / `depth` | **0 / 0.0** | 0 | OK |

即：绘制没超预算、视频没掉帧、排版不叠压、帧间隔均值达标 —— **判据全绿，但用户看到的就是不匀**。
说明「均值类」指标对这类缺陷是盲的。

### 根因：面板是 170Hz，帧循环是写死的 16ms

新写的 `tool/frame_pacing_probe.cpp` 直接量显示与合成节拍（用户本机实测）：

```
EnumDisplaySettings(CURRENT): 2560x1440 @ 170 Hz (5.882 ms)
DWM: qpcRefreshPeriod=58823.0 -> 5.882 ms (170.00 Hz)
```

而 `main.cpp:261` 的帧节拍是常量：

```cpp
constexpr int kFrameIntervalMs = 16;  // ≈62.5fps，对齐 60fps 的显示刷新
```

这句注释里的前提**从一开始就不成立**：16ms 是 62.5Hz，与 60Hz（16.667ms）也差 4%，
与本机 170Hz 更是差到 2.72 倍。于是：

- 弹幕层每秒只产出 **61.3 帧**，面板每秒合成 **170 帧**；
- 每帧在屏停留 `170 / 61.3 = 2.77` 个刷新周期 —— **不是整数**；
- 按 2.77 拆解，**77% 的帧停留 3 个刷新周期、23% 停留 2 个**；
- 于是「屏幕上看得见的位移步长」在 3 个周期 / 2 个周期之间交替：
  以 2560 宽、`speed_px = 2560/8 = 320 px/s` 计，
  步长在 **5.65px 与 3.76px 之间跳**（±33% 幅度、约 **14 次/秒**）。

这正是「滚动文字看起来在抖」的经典成因（2:3 pulldown 型抖动）：
**平均帧率完全正确，但每一帧被显示的时长不相等**。眼睛对「停留时长不均匀」比对
「帧率低」敏感得多 —— 均匀的 85Hz 看起来比不均匀的 61Hz 平滑。

`frame_pacing_probe.cpp` 的同机对照（同一台机器、同一面板）：

| 策略 | mean | 刷新桶分布 | 结论 |
|---|---|---|---|
| A：现状（16ms 周期可等待定时器） | 16.355 ms | **3x:100%**（与 5.882ms 错拍） | 每帧都偏离整数个刷新周期 |
| B：每次提交后 `DwmFlush()` | 5.883 ms | **1x:100%** | 与刷新同相，无节拍偏差 |

> 注：探针里「非 1x 帧占比 100%」是按「帧间隔应等于整数个刷新周期」这一理想判据算的
> 相对值，用来对比两种策略，不代表每秒真有 61 次可感知停顿；可感知的是上面算出的
> 「23% 的帧只停留 2 个周期」。

### 次要成因：位移取整带来的 ±0.5px 脉动

`main.cpp:5025` 贴图时把位置取整：

```cpp
BlendDanmakuTexture(surface, *item.texture, std::lround(x), std::lround(y), ...);
```

`x` 本身是浮点（`x = width - (now - appear) * speed_px`），到贴图这一步被量化到整像素。
以 170Hz 面板、85Hz 节拍（步长 3.76px）为例，整数步长序列是 `4,4,3,4,4,4,3,4,4…`
—— 约 22% 的帧少走 1px（幅度 25%，频率 ~19Hz）。

`lround(绝对位置)` 已经是最小 RMS 误差的量化方式（等价于误差扩散），所以这一项
**不能靠改取整方式消除**，要真正消掉只能做亚像素采样（见「技术方案 · 路线二」）。
量级上它比上面那条拍频小，属次要项。

## 目标

- 弹幕层的每一帧在屏停留**整数个**刷新周期，位移步长恒定 —— 消除 2:3 拍频；
- 帧产出节拍与 DWM 合成节拍**同相**，不再自由漂移；
- 覆盖率：60 / 75 / 120 / 144 / 165 / 170 / 240Hz 面板都自动选到合适分频；
- 绘制开销有上界（不因为追刷新率而把单核吃满）；
- 把「帧节拍是否与刷新同源」变成常驻断言，防止回退。

## 非目标

- 不改弹幕排版、字号、速度、轨道规则（`overlap`/`depth` 已达标）；
- 不改应用侧（Flutter）与 Android；
- 不引入插值 / 运动模糊（那是「让 61Hz 看起来平滑」的另一条路，代价是拖影）；
- 不动 mpv 的 `video-sync`（视频侧是否也需要 `display-resample` 是独立议题，见「遗留」）。

## 技术方案

### 路线一：把弹幕帧节拍锁到刷新率的整数分之一（推荐）

1. **取真实刷新周期**：`DwmGetCompositionTimingInfo(nullptr, &info)` → `qpcRefreshPeriod`
   （QPC 单位，转 ms）；失败时退回 `EnumDisplaySettingsW(…, ENUM_CURRENT_SETTINGS, &dm)`
   的 `dmDisplayFrequency`。在 `WM_DISPLAYCHANGE` 时重取（换显示器 / 改刷新率 / 进全屏都要）。
2. **选分频**：`divisor = max(1, (int)ceil(refresh_hz / 90.0))`，帧节拍 = 刷新率 / divisor。
   - 60Hz → 1 → 60Hz ｜ 75 → 1 → 75 ｜ 120 → 2 → 60 ｜ 144 → 2 → **72** ｜
     165 → 2 → **82.5** ｜ 170 → 2 → **85** ｜ 240 → 3 → 80
   选 `ceil(refresh/90)` 而不是取最高刷新率，是为了让开销有上界：170Hz 面板按 1:1 走
   需要 `170 × 3.15ms ≈ 536ms/s`（约 54% 单核）—— 代价偏高且对滚动文字收益有限。
   **关键不是频率高低，而是「整数分频 + 同相」**。
3. **相位锁定用 `DwmFlush()`，不要用周期定时器**：`refresh/2 = 11.76ms` 这种周期喂给
   `SetWaitableTimer` 只能取整毫秒（12/11 交替）→ 又造出一个新的错拍。改成：
   每轮 `DwmFlush()` 等一个合成边界，**计满 `divisor` 个刷新周期才真绘一帧**，
   其余轮次只处理消息。这样 dwell 恒为 `divisor` 个周期、相位与合成器一致。
4. **重绘判断**：只在「弹幕层确实要动」时才 `PaintDanmaku()`（暂停 / 无在屏条目 /
   缓冲时不必重绘）—— 现有代码已有 dirty 概念，用它避免空转。
5. **延迟优化（可选）**：`DwmFlush()` 返回即「刚合成完」，此时提交的内容要等下一个
   vblank 才可见（+1 周期延迟）。要压低延迟可用 `DwmGetCompositionTimingInfo` 的
   `qpcVBlank` / `cRefresh` 预测下一个 vblank，在其**前** ~1ms 提交。属二阶优化。

### 路线二（可选，独立于路线一）：亚像素位移

把 `BlendDanmakuTexture` 的整数贴图换成「整数部分 + 相位」：
预先为每个纹理栅格化 N 个相位变体（如 N=4，向右偏移 0 / 0.25 / 0.5 / 0.75px），
绘制时按 `frac(x)` 选最接近的那张、按 `floor(x)` 定位 → 位移量化误差从 ±0.5px 降到 ±0.125px。
代价：纹理内存 ×N、栅格化成本 ×N（一次性）。**建议先只做路线一**，
实机看过后再定是否需要它。

### 未选方案

- **保持 16ms，只把 `avg` 判据收紧**：指标收紧不改变观感，属于自欺。
- **周期定时器取整到刷新周期**（170Hz → 6ms）：6ms vs 5.882ms 仍差 2%，
  每 ~50 帧错一拍 —— 错拍只是变慢，没有消失。
- **无限提高绘制频率到 170Hz**：见上，CPU 代价翻倍而观感收益小。
- **让弹幕跟着视频帧走**：视频 24fps 时弹幕也只有 24Hz，更抖。

## 风险与回滚

- 主要风险：
  1. `DwmFlush()` 在 DWM 被禁用 / 远程桌面下可能立即返回 → 会变成满速空转。
     缓解：拿不到 `qpcRefreshPeriod` 时不启用该路径（退回现有定时器）；
     并在循环里加「一轮至少等 0.5ms」的下限。
  2. 提高节拍后弹幕层 CPU 占用上升（85Hz 约为现状的 1.4 倍）。缓解：分频上界 90Hz；
     并保持「无变化不重绘」。
  3. 刷新率在播放中变化（插拔显示器 / 显卡驱动切模式）→ `WM_DISPLAYCHANGE` 里重取。
- 监测方式：`MOVA_DANMAKU_DRAW`（既有）+ 新增的 pacing 字段 + `frame_pacing_probe.exe`。
- 回滚步骤：还原 `main.cpp` 的帧循环与分频逻辑。

### 结论

「不够平滑」的主因不是帧率不够、不是绘制超预算、也不是排版问题，
而是**帧节拍与面板刷新率不同源**：61.3fps 的产出喂给 170Hz 的合成器，
每帧停留 2.77 个刷新周期（非整数），导致 23% 的帧停留时长只有其余帧的 2/3，
位移步长以约 14 次/秒的频率在 ±33% 之间跳。

既有判据（`avg ≤ 18ms` / `late33 < 3` / `draw ≤ 12ms` / `drop == 0`）全部
通过 —— **它们的盲区正是「每帧被显示的时长是否相等」**，这也是 2026-09-19 那轮
把时间源换成 QPC 之后依然没解决的残量：QPC 保证的是「位置算得准」，
不保证「像素什么时候被投到屏幕上」。

1. 视频侧现已设置 `video-sync=display-resample` 与 `interpolation=yes`，尝试让画面节奏
   贴合显示刷新。合成诊断场景没有观察到 mpv 丢帧，但不等于真实片源、音视频同步和硬件解码

2. 亚像素位移（路线二）未做，待路线一实机确认后再定。

### 结论（与上一节的初步结论不同，以此为准）

上一节把根因定为「节拍与刷新率不同源」，修法定为「锁整数分之一拍」。
实测推翻了其中「只要锁上就够」的部分：

1. **不是 DWM 被降频**：`compose = 5.88–5.91ms` 与面板周期一致，DWM 的目标节奏
   就是 170Hz。
2. **不是认错了面板**：`monitor=\\.\DISPLAY1 hz=170 primary=yes`，窗口在 170Hz 主屏上。
3. **是 `DwmFlush` 自己在漏拍**：每次调用等 1 拍约 50%、等 2 拍约 48%（双峰），
   均值 1.43 拍 ≈ 118Hz。
4. **根本约束是「一轮循环的耗时」**：把 flush 返回点记作 `kT+λ`，则主循环每轮
   恰好锁 1 拍的**充要条件是 `λ + o < T`**（`o` = 该轮 flush 之外的工作量）。
   本机 `o ≈ 6.6ms > T = 5.882ms`，条件必然不成立 → 每轮要么 1 拍要么 2 拍，
   由 `o` 的抖动决定 → paint 间隔以 2/3/4 拍不规则混合。

即：**170Hz 的 1:1 满刷新在这台机器上、以当前循环结构不可达**。
仅弹幕层绘制（2.8–3.7ms）+ ULW 贴图（0.65–0.93ms）就占掉约 3.6ms 的 5.88ms 预算，
再加上消息泵与 `TickFrame`，`o` 已是面板周期的 1.1 倍以上。

### 最终实现：85Hz 固定周期节拍时钟（方案 A，已落地并实测达标）

用户否掉了 1:1，改按方案 A 实现。

**做法（`main.cpp`）**

- `FrameDivisorFor` 改回 `ceil(refresh_hz / 90)` → 60Hz:1x、**170Hz:2x（85Hz）**、240Hz:3x。
  上界取 90Hz 而不是 170Hz，理由就是上面的 `λ + o < T` 条件：170Hz 的 1:1 要求一轮
  循环里 flush 之外的工作量不到 5.882ms，本机做不到。
- 新增节拍时钟 `g_pacing_timer`：`CreateWaitableTimerExW(..., 
  CREATE_WAITABLE_TIMER_HIGH_RESOLUTION, ...)`，**周期 = divisor × 刷新周期**
  （170Hz/2 → 11.764ms，正好是 100ns 的 117647 个单位，可精确表达）。
- `ArmNextPacingTick()` 每轮用 **100ns 精度的相对到期时间**重排，目标时刻一律从锚点算
  （`anchor + tick × period`），**不用** `SetWaitableTimer` 的 `lPeriod`（单位是整毫秒，
  11.76ms 只能喂 12/11 交替 → 又错拍）。
- 相位只在 `RebuildPacingTimer()` 里用一次 `DwmFlush()` 对齐（flush 返回时刚过合成边界），
  之后靠「周期严格等于整数拍」保持同相。**主循环里不再每轮 `DwmFlush`。**
- 主循环改成 `MsgWaitForMultipleObjects(1, &g_pacing_timer, FALSE, INFINITE, QS_ALLINPUT)`：
  定时器（index 0）优先于消息（index 1），既不会因为一直在处理消息而饿掉 tick，
  又能让消息一到位就处理。`FramePacingWanted()` 为假时走原 `frame_timer` 路径。
- 诊断：`flush=` / `fhist=`（DwmFlush 拍数直方图）**已删除** —— 既然不再按它计拍，
  留着就是误导性仪表。新增 `tick=`（实测 tick 间隔，均值/次数），用来区分
  「时钟没跑对」和「画与拍对不上」。

**实测（lavfi 1080p，`--hwdec=auto-safe`，稳态）**

| 量 | 16ms 定时器（改前） | 1:1 `DwmFlush`（废弃） | **85Hz 固定时钟（现在）** |
|---|---|---|---|
| `avg` / 帧率 | 16.3ms / 61fps | 14.8ms / 67fps | **11.76ms / 85.0fps** |
| `dwell` 集中度 | 3:2 交替，~77% 停 3 拍 | 仅 4–8.5% 恰 1 拍 | **稳态 91.1% 恰 2 拍** |
| `late33` | 0 | 0–4 | **0** |
| `draw`/`post` | 2.6ms / — | 2.8–3.7ms | 2.7–3.3ms / 0.65–0.84ms |
| 判据 | 均值类全绿（盲区） | 拍数断言 BAD | **`VERDICT OK frame clock locked to the panel`** |

`MOVA_FRAME_PACING=refresh=5.882ms divisor=2 hz=170.0 period=11.764ms monitor=\\.\DISPLAY1 hz=170 primary=yes`

`tick=11.77ms`、`paints/tick=1.00` —— 时钟与绘制一一对应，二者都对上了。

### 两个实现期的坑（都已修）

1. **锚点只在「真的漏拍」时才挪。** 最初的 `ArmNextPacingTick` 只要迟到（`delay < 0.05ms`）
   就重设锚点，等于把这一拍的迟到量固化进后续所有日程 → 实测 tick 周期变成
   **11.83ms 而不是 11.764ms**（+0.6%）；这点偏差每 60 拍累积约 4ms，相位会缓慢滑过拍
   边界，于是部分帧掉到 3 拍。改成 `delay < -period × 0.5` 才重设锚点、其余情况只夹到
   0.05ms，让下一次的 delay 自动把迟到补回来 → tick 立刻回到 11.77ms。
2. **判据必须只看稳态窗口。** 开头两个窗口还在铺弹幕、时钟刚对相位，把它们一起平均，
   集中度会从 **91% 被拉到 55%**，于是「已经达标」被读成 BAD。探针与套件都改成取末尾三个窗口。

### 复测：把「均值」换成分布之后才看得见的东西

85Hz 那版落地的第一次全套跑出来仍然 BAD：`稳态停留 2 拍的帧占 25.6% (46/180)`，
`dwell=[23,14,23,0]` —— **1 拍与 3 拍交替**，均值照样精确等于 2 拍
（`23×5.88 + 14×11.76 + 23×17.64 = 60×11.76`）。这一条把问题从「时钟对不对」
推进到「是时钟在抖，还是绘制被推迟」，于是补了三组诊断：

**1. 隔离实验：定时器机制本身稳不稳？**（`tool/frame_pacing_probe.cpp` 扩展）

| 策略 | 周期 | cv | dwell 分布 |
|---|---|---|---|
| A 现状（`lPeriod=16ms`） | 16.363ms | 0.0317 | 3x: 98.4%（与 5.882ms 错拍） |
| B 每条一次 `DwmFlush` | 5.882ms | 0.0281 | 1x: 100% |
| **C 高精度定时器 + 绝对日程，空转** | 11.765ms | 0.0693 | **2x: 98.8%** |
| **D 同上 + 每拍 3ms 绘制负载** | 11.766ms | 0.0328 | **2x: 100.0%** |

C/D 与 `ArmNextPacingTick` 同构。D 带 3ms 负载时 **100% 落在 2 拍** ——
**定时器机制本身没有问题**，抖动不可能来自「高精度定时器不准」。

**2. 应用侧补同源的节拍分布**（`MOVA_DANMAKU_DRAW` 新增字段）

- `tickdwell=1,2,3,4` / `tkmax=`：**tick 间隔**的拍数分布（与绘制 `dwell` 配对读）。
  两者都塌在 `div` 拍 = 真的锁住了；tick 散 = 主循环调度；tick 齐而绘制散 = 绘制被推迟。
- `ptph=` / `ptjit=`：`PaintDanmaku` 相对**本拍 tick 时刻**的滞后（均值 / 极差）。
  tick 整齐而 dwell 散时，滞后极差就是「提交相位在漂」的直接证据。
- `mw=`：主等待被「消息」唤醒（而不是被定时器唤醒）的次数。这类返回**不复位定时器**，
  定时器保持触发态、下一轮立刻再返回一次 —— 天然造出「一个短间隔 + 一个长间隔」。

**3. 复测结果（同一构建连跑三次，每次 8s 稳态）**

| 指标 | 第 1 次 | 第 2 次 | 第 3 次 |
|---|---|---|---|
| 稳态停留 2 拍的帧占 | 96.7% | 97.2% | 96.1% |
| 稳态 2 拍的 tick 占 | 96.7% | 96.7% | 95.0% |
| `tkmax` | 12.55ms | 14.48ms | 14.99ms |
| `ptph` / `ptjit` | 0.13 / 0.14ms | 0.12 / 0.18ms | 0.12 / 0.20ms |
| `mw` | 26 | 26 | 38 |
| 判定 | **OK** | **OK** | **OK** |

`ptph ≈ 0.12ms`、`ptjit ≈ 0.2ms` —— 绘制**紧贴** tick 发生且相位漂移只有 0.2ms，
说明绘制派发路径（WM_PAINT 低优先级）在本机不是瓶颈；`mw` 有 26–38 次/60 拍也
没有被它带歪。残余的 3–4% 是孤立调度抖动（`tkmax` 12.5–15ms 的单次迟到），
**不是**系统性的 1/3 交替。

> **重要更正**：上一轮那条 `25.6% / dwell=[23,14,23,0]` 是**负载污染的测量**，
> 不是稳定复现的行为。它跑在刚结束一次 41s Flutter 构建之后，同批样本里
> `gap` 峰值 19–21ms、`late20` 有非零值；现在同一实现三次都稳定在 96–97%、
> `late20` 全 0。**结论：判节拍类指标必须在机器空闲时测**，否则会把调度抖动
> 读成实现缺陷（这次的代价是差点去改一个没坏的绘制派发路径）。

### 判据重新基线化（需知悉）

`late20` / `late33` 是 60fps 时代留下的**绝对**门槛。走节拍时钟后目标节拍是
`divisor × 刷新周期`（本机 11.76ms），20ms 只有 1.7 拍，一次调度抖动就踩线 ——
它拦不住真缺陷，只会让用例随机变红。因此：

- 节拍路径（拿得到刷新率）**改由「停留拍数是否集中在 div 拍」直接断言**（≥85%）；
- 非节拍路径（拿不到刷新率）仍按 `late20 > 6` 老门槛判，行为不变；
- 两处改动：`tool/verify_segments_and_danmaku.py` 的 `06_danmaku_frame_pacing`、
  `tool/probe_danmaku_layout.py`。

这不是「为了变绿而放宽」：覆盖没有被削弱，而是把「标错尺度的代理指标」换成了**直接量**。
`late33 ≥ 3`（= 2.8 拍，确属停顿）仍然照旧判 BAD。

### 遗留

3. `DWM_TIMING_INFO.cFrameDisplayed` 在本机不推进（恒为 0），因此**没有**可用的
   「实测合成 fps」。别再用它算 fps —— 之前加过一版，报出来一直是 0，
   看起来像「合成器没在合成」。判断合成器节奏请用 `compose`。
4. 视频已使用 `display-resample` 与插帧；下一步应在用户报告卡顿的真实片源和设备上确认，
   并区分网络/磁盘缓冲、解码负载、显示同步与弹幕渲染，不应仅依据合成 lavfi 场景归因。
5. 位移取整的 ±0.5px 量化（本文档「次要成因」一节）仍未做亚像素方案。
   85Hz 下步长约 3.8px，整数步长序列是 `4,4,3,4,4,4,3,4,4…`，约 22% 的帧少走 1px。
   **这是目前弹幕侧唯一已知的、与节拍无关的残余抖动源**；要做就做路线二。

### 视频与弹幕联合诊断（2026-09-23）

Windows Release 加入 mpv `video-sync=display-resample`、`interpolation=yes` 后，使用
`probe_danmaku_layout.py` 对 1080p 合成动态视频执行 10 秒采样：15 个采样窗口，
弹幕绘制峰值 0.72ms、post 峰值 0.54ms，帧节拍均值 11.77ms，`drop=0`，停留拍数集中度

主观/客观确认。`display-resample` 会匹配显示刷新节奏，插帧可能增加 GPU 工作量，实际效果受

# 视频缓存改为播放头前向滚动窗口

## 基本信息

- 标题：视频缓存改为播放头前向滚动窗口
- 日期：2026-09-30
- 状态：实现中（代码完成，待双端实机确认）
- 影响平台：Windows / Android
- 关联 Issue、提交或版本：当前播放缓存策略

## 背景与问题

当前 `VideoCacheStore` 从媒体字节 0 开始，只下载到设置容量后就停止。它既没有以当前播放位置为缓存窗口起点，也不会在播放消耗缓存后继续向后补充；续播时仍会把上次从片头开始的部分文件当成缓存。因此设置的“视频缓存上限”无法准确表达当前集播放头前方可预读的容量。

## 目标

- 每集缓存窗口从当前播放位置开始，窗口长度不超过设置容量，且不超过媒体剩余大小。
- 播放消耗到窗口约一半时，滚动窗口至当前播放位置并继续向后预读，直到接近本集结尾。
- 任意时刻只保留当前集的一个缓存窗口；窗口替换时先释放旧窗口，缓存缺口由现有源站 Range 回退供播放，不等待缓存下载。
- 本集自然播放完成后删除该集缓存；手动暂停、退出或切集不作为自然完成。

## 非目标

- 本次不将整集离线保存；容量的含义是当前播放位置前方的窗口大小，不是整集累计下载量。
- 本次不改缓存容量档位、总缓存目录、网络策略或下一集预热大小。
- 本次不改变播放器选择资源及播放服务器的逻辑。

## 用户流程与界面

用户正常播放或从续播点开始播放。播放器在后台缓存当前播放点之后最多一个设置容量的前向窗口；消耗约一半窗口后移至当前播放点并补缓存。窗口请求失败不影响播放，代理继续回源。自然播完后删除当前集缓存；中途退出或手动切集则保留最后一个窗口供续播使用。现有设置页继续按档位显示容量，辅助文案解释为“播放点前方窗口上限”。Windows 和 Android 均沿用原有控件与输入方式，无新增 UI。

## 数据与接口

- 输入与输出：媒体 URL、请求头、播放位置/时长、媒体字节总长和容量；输出为本地有界字节窗口及缓存状态。
- 数据来源：播放器实时位置与时长；源站 `Content-Range` / `Content-Length`。
- 新增/修改字段：缓存进度增加窗口绝对起始字节；元数据增加 `startBytes`。
- 持久化键或缓存格式：偏好键不变。新窗口使用独立文件后缀和元数据，旧 `.bin`、`.part` 仍按原格式读取；旧 `.part` 缺少 `startBytes` 时视为从 0 开始。
- 网络接口、超时与错误处理：优先用带现有鉴权头的 Range 请求发现总长并下载指定窗口；服务端不支持 Range 或总长未知时退回从头开始的旧式有界预读。失败保持已有播放器源站回退，不阻塞播放。
- 隐私与敏感信息：新窗口侧车元数据只记录字节边界、标题和时间，不保存 URL 或请求头；完整缓存沿用当前元数据格式，缓存文件名仍使用 URL 哈希。

## 技术方案

- `video_cache.dart` 实现位置/时长到字节位置的纯函数、范围缓存读写、窗口元数据、窗口下载及按 URL 删除。
- Android 共用 `PlayerPage` 在播放位置推进到窗口一半时取消旧任务并启动新窗口；监听自然完成事件清理缓存。
- Windows 原生播放器宿主使用相同缓存 API，按 `MOVA_POSITION` 更新窗口；自然 EOF 后清理对应集的缓存。
- 代理只在请求 Range 完整落于本地缓存窗口时从本地回应；其他 Range 仍回源，不把未下载的部分误报成 EOF。
- 进度展示继续按窗口内下载比例；Windows 时间轴使用窗口绝对终点/媒体总长计算缓存位置。

## 兼容与迁移

- 旧版本数据是否可继续读取：是。完整 `.bin` 可继续播放；旧 `.part` 视作起点 0 的缓存前缀，新缓存写到不同后缀，不会将非零起点字节误当作片头。
- Windows / Android 差异：Windows 自然完成由原生播放器 EOF 消息识别，进程退出时重试删除；Android 使用 media_kit 自然完成状态。共享缓存格式与回退行为相同。
- 回滚后是否安全：是。旧版本忽略新窗口文件，仍可读取旧 `.bin` / `.part`。新格式缓存仅在新版本中复用。
- 是否需要迁移、清理或功能开关：无需迁移；自然完成仅删除当前 URL 对应缓存，不清理其他剧集。

## 风险与回滚

- 主要风险：播放时间到字节位置是基于媒体总字节数和时长的估算，VBR 媒体的实际映射不是严格线性的；服务端可能忽略 Range。
- 监测方式：测试 Range 区间与元数据边界；人工确认大码率、续播与切集场景不阻断播放。
- 回滚步骤：回退缓存窗口调用与新格式读写；旧 `.bin` / `.part` 不受影响，新 `.window.part` 文件可由设置页清理。

## 实现记录

- 新缓存写入独立的 `.window.part` 与 `.window.json`，带 `startBytes`；旧 `.bin` 与 `.part` 仍按起点 0 读取。缓存代理仅对完整落在缓存范围内的有界 Range 本地响应，其余请求回源。
- Android 播放页与 Windows 原生宿主都按“播放位置 / 时长 × 媒体字节总量”估算播放头字节位置；到窗口一半后滚动窗口，并保留上一段回退网络播放所需的代理。
- Android 监听 media_kit 自然完成状态；Windows 按原生 EOF 消息识别自然完成。两端仅删除对应 URL 缓存；退出、暂停和手动切集保留缓存。
- 设置页说明已改为当前播放点前向窗口语义。服务端不支持 Range 时退回起点窗口，停止无效滚动请求。
